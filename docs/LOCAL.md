# Local test cluster

Prod reconciles `master`, so a bad merge breaks the lab. Every change is
verified on a throwaway local cluster first, then diffed against prod, and only
then merged.

## Setup (once)

`local/cluster.sh` re-execs itself in the flake's `local` devShell
(`nix develop ./nix#local`), so `limactl`, `kubectl`, `flux`, `kustomize`,
`kubeconform`, `sops`, `wg`, ... come from `nix/flake.lock`, the same pins CI
uses. Only Nix and the operator age key in `~/.config/sops/age/keys.txt`
(decrypts the same secrets prod uses) are needed on the host.

For amd64-only images (e.g. `mokuro-bunko`), install Rosetta *before* the VM is
created: `softwareupdate --install-rosetta --agree-to-license`.

```sh
local/cluster.sh up        # VM + k3s + flux, then syncs the working tree (~10 min first time)
```

## Workflow

1. **Branch** — work on a feature branch / worktree, never on `master`.
2. **Static checks** — `local/cluster.sh check`: the CI checks
   (`kustomize build | kubeconform` per stage), an eval of every NixOS host, and
   `nix flake check`.
3. **Upgrade path** — `local/cluster.sh sync master` puts the local cluster in
   prod's current state first, so the next step tests the transition and not
   just a fresh install.
4. **Apply locally** — `local/cluster.sh sync`: pushes `cluster/` from the
   working tree (uncommitted changes included) and waits until every Flux
   Kustomization has applied that revision and every HelmRelease, Deployment,
   StatefulSet and DaemonSet is healthy. Non-zero exit with a report otherwise.
   Poke around with `local/cluster.sh kubectl|flux|k9s ...`.
5. **End-to-end checks** — `local/cluster.sh verify`: exercises what a healthy
   rollout does not prove (see [Fixtures](#fixtures)). Run it for changes
   to gluetun, qBittorrent, the arr stack or the network path between them.
6. **Diff against prod** — `local/cluster.sh diff`: read-only server-side dry
   run of the working tree against prod. It shows exactly what will change once
   merged.
7. **PR** — push the branch and open a PR; CI repeats the static checks.
8. **Merge and watch** — after merging, watch `flux get ks` / `flux get hr -A`
   on prod. Roll back with `git revert` + merge, never by editing the cluster.

`up` also registers a `lab-local` context in `~/.kube/config` (override with
`KUBECM_CONFIG`), so `kubecm switch lab-local` / `kubectx lab-local` work;
`destroy` removes it again. `diff` always uses `~/.kube/lab` (override with
`LAB_PROD_KUBECONFIG`), never the current context.

`local/cluster.sh stop` keeps the VM for next time; `destroy` deletes it.

## How it maps to prod

| | prod | local |
|---|---|---|
| k3s | `services.k3s.package` from the flake | same version (read from the flake), same flags, embedded etcd |
| Nodes | 5 | 1, named `nix-optiplex2` (jellyfin's nodeSelector) |
| Flux | `fluxVersion` in `nix/modules/flux.nix` | same install.yaml, sha256 verified |
| Source | GitRepository `master` | OCIRepository from an in-cluster registry, pushed by `sync` |
| Stages | `nix/config/manifests/flux-sync.yaml` | same file, patched by `local/flux/` |
| `cluster-settings` | generated in `flux.nix` | same, but `NFS_HOST` = VM, `EXTERNAL_DOMAIN` = `lab.test` |
| NFS | `nix-optiplex1:/tank` | NFS server in the VM, same exports and NFS versions |
| Secrets | `sops-age` from `nix/secrets/sops-age.enc` | same secret |

## What is different on purpose

Everything that would touch something shared with prod, or that the single
node cannot satisfy, is patched in `local/flux/patches/` (the only place for
such overrides):

- **Tailscale**: operator, its OAuth secret, the ProxyGroup and `traefik-public`
  are removed; they would join the real tailnet.
- **cert-manager**: ClusterIssuers are self-signed and the Cloudflare token is
  removed, so no ACME requests or DNS-01 records.
- **gluetun**: connects to a local WireGuard server (see [Fixtures](#fixtures))
  instead of Mullvad; a second peer with prod's Mullvad WireGuard key breaks
  prod's tunnel. Its Secret is generated by `cluster.sh`, not taken from git.
- **qBittorrent**: its WebUI login is seeded from the arr secret on start
  (prod's was set by hand), so Sonarr can connect to a fresh install.
- **PostgreSQL (CNPG)**: `podAntiAffinityType` is `preferred` instead of
  `required`, so both instances fit on the single node and replication is
  still exercised.
- **arr-config CronJob**: talks to the apps through their (self-signed)
  ingress URLs, so TLS validation is relaxed: `CERT_VALIDATION=disabledForLocalAddresses`
  for Sonarr/Prowlarr, `CURL_INSECURE` for the host-config step and
  `NODE_TLS_REJECT_UNAUTHORIZED=0` for Configarr.

If you add something that talks to an external account with prod credentials,
add an override there in the same change.

## Fixtures

`local/fixtures/` holds local stand-ins for external services, so the
workloads that need them can run for real instead of being switched off.
`cluster.sh sync` applies them with kubectl (outside Flux) together with the
Secrets it generates; keys live in `local/.state/vpn` and survive syncs.

- **vpn-endpoint** (ns `local-fixtures`, `10.43.0.51:51820/udp`): a WireGuard
  server that NATs into the pod network. gluetun uses it as a `custom`
  provider with the same firewall settings as on prod.

`local/cluster.sh verify` checks, and fails on the first problem:

1. A 2 MB download from the qbittorrent container works, and at least that
   many bytes passed the VPN endpoint (traffic uses the tunnel).
2. Kill switch: with `wg0` down on the endpoint, the qbittorrent container
   cannot reach `1.1.1.1` until 30s after gluetun has noticed and restarted
   the VPN (~3 min; the restart is when a leak would happen), and traffic
   resumes once `wg0` is back.
3. `https://q.<domain>` accepts the qBittorrent login from the arr secret.
4. A one-off `arr-config` job (Configarr) succeeds with the download client
   enabled, and Sonarr's download client test passes.

Not covered: Mullvad itself (server list, `SERVER_CITIES`), and real
torrent traffic. For a gluetun major, a separate Mullvad device key (never
prod's) in a local-only Secret would cover the provider path.

## Not covered

- **NixOS host changes** are only evaluated (`check`), not booted. Deploy them
  with `nix/scripts/rebuild.sh <host>` one host at a time, the non-bootstrap
  hosts first.
- **MetalLB / public exposure**: the VM is behind NAT, so LoadBalancer IPs are
  assigned but unreachable; the edge relay path cannot be tested.
- Multi-node behaviour (scheduling across nodes, etcd quorum).
